Algorithm Design Techniques

A design technique is a general strategy for building an algorithm. Knowing the handful of classic strategies lets you recognize a new problem as a variation of one you already know how to solve.

§The big picture

Most algorithms you'll ever write are an instance of one of about ten strategies. They differ in how they break a problem down and how much work they repeat or avoid. Here's the whole landscape on one table — the rest of the page expands each row.

1Brute force & exhaustive search

Generate every candidate solution and check each one. Simple, always correct, and almost always too slow for large inputs — but it's the honest baseline every other technique is measured against.

  • Examples: linear search, selection & bubble sort, naïve substring matching, trying all n! city orders in the Travelling Salesman Problem (TSP), password cracking.
  • Cost: grows explosively — subsets are O(2ⁿ), permutations O(n!).

Why it still matters

For small n, brute force is the right choice — it's simple and bug-resistant. And writing it first gives you a correct reference to test your clever algorithm against.

2Decrease & conquer

Reduce the problem to a single smaller instance, solve that, then extend the solution. The link between the problem and its sub-instance is exploited top-down or bottom-up.

VariantHow much you decreaseExample
By a constantn → n−1Insertion sort, DFS/BFS
By a constant factorn → n/2Binary search, exponentiation by squaring
By a variable amountdepends on the dataEuclid's GCD, quickselect

Binary search is the poster child: each step throws away half the remaining data, giving O(log n).

3Divide & conquer

Split the problem into several independent subproblems of the same kind, solve each recursively, then combine their answers. The subproblems must not overlap — that's what separates this from dynamic programming.

  • Examples: merge sort, quicksort, binary tree traversals, Karatsuba multiplication, Strassen's matrix multiply, the Fast Fourier Transform.
  • Cost: often analysed with the Master Theorem; many give O(n log n).

4Transform & conquer

First transform the instance into something easier to work with, then solve. Three flavours:

  • Instance simplification — e.g. pre-sort the data so the real work becomes trivial (finding duplicates, closest pair).
  • Representation change — store data in a smarter structure: heaps (heapsort), balanced BSTs, hash tables.
  • Problem reduction — convert problem A into a solved problem B, e.g. lcm(a,b) = a·b / gcd(a,b), or modelling something as a graph/flow problem.

5Greedy

Build the solution step by step, always taking the choice that looks best right now, and never reconsidering. Fast and simple — but only correct when the problem has the greedy-choice property and optimal substructure.

  • Works (provably optimal): Dijkstra's shortest paths, Huffman coding, Kruskal/Prim minimum spanning trees, activity selection, coin change for canonical coin systems (like US coins).
  • Fails: 0/1 knapsack, and coin change for arbitrary denominations — locally best ≠ globally best.

In this repo

greedy_coin.py takes the biggest coin that fits, repeatedly. For US coins that's optimal; change the denominations and the same greedy code can return too many coins — a perfect illustration of greedy's limits.

6Dynamic programming

When subproblems overlap (the same sub-question is asked many times), solve each one once and store the answer. Requires overlapping subproblems + optimal substructure.

StyleDirectionHow
MemoizationTop-downRecurse, but cache each result the first time you compute it.
TabulationBottom-upFill a table from the smallest subproblems upward.

Naïve recursive Fibonacci recomputes fib(2) exponentially many times — O(2ⁿ). DP computes each fib(k) once — O(n).

fib(5)
├─ fib(4)
│  ├─ fib(3)
│  │  ├─ fib(2) ← recomputed
│  │  └─ fib(1)
│  └─ fib(2) ← recomputed again!
└─ fib(3) ← and again…   →  DP stores each value once

Examples: 0/1 knapsack, longest common subsequence, edit (Levenshtein) distance, matrix-chain multiplication, Bellman-Ford & Floyd-Warshall shortest paths.

Greedy vs DP vs Divide & conquer — in one line

Divide & conquer: subproblems are independent. DP: subproblems overlap, so cache them. Greedy: never even look back — one pass of local choices.

7Backtracking

Build a solution one decision at a time, exploring a state-space tree. The moment a partial solution can't possibly become valid, prune it and back up. This avoids exploring the full brute-force space.

Examples: N-Queens, Sudoku solvers, generating permutations/combinations, the subset-sum problem, graph colouring, maze solving.

8Branch & bound

Backtracking's cousin for optimization problems. As you explore, you keep the best complete solution found so far and compute a bound (best possible value) for each branch. If a branch's bound can't beat the current best, discard the entire branch unexplored.

  • Examples: exact TSP, 0/1 knapsack (for the true optimum), integer linear programming, assignment problems.
  • Difference from backtracking: backtracking prunes branches that are invalid; branch & bound also prunes branches that are valid but provably suboptimal.

9Randomized algorithms

Make random choices during execution. Two families:

TypeCorrectnessRunning timeExample
Las VegasAlways correctRandom (fast on average)Randomized quicksort
Monte CarloProbably correctFixed / boundedMiller-Rabin primality, Monte Carlo simulation

In this repo

The poker simulator and tsp.py simulate are Monte Carlo methods: they sample many random outcomes (hands dealt, city orders shuffled) and aggregate the results to estimate an answer rather than computing it exactly.

10Approximation & heuristics

For NP-hard problems where the exact optimum is too expensive, settle for a solution that is provably close (approximation algorithms) or just empirically good (heuristics/metaheuristics).

  • Approximation algorithms come with a guarantee — e.g. a 2-approximation for metric TSP (build a route from a minimum spanning tree) is never worse than twice optimal.
  • Heuristics & metaheuristics have no guarantee but often work well: hill climbing, simulated annealing, genetic algorithms, ant-colony optimization.

In this repo

tsp.py tackles an NP-hard problem by random sampling and keeping the shortest tour found — a heuristic. "How many simulations?" is exactly the approximation trade-off: more runs → better answer, with diminishing returns.

★How to choose a technique

Walk these questions roughly in order:

  1. Is the input small, or do I just need a correct reference? → Brute force.
  2. Can I cut the problem to one smaller piece each step? → Decrease & conquer.
  3. Can I split into independent pieces and combine? → Divide & conquer.
  4. Would a different representation make it easy? → Transform & conquer.
  5. Optimization where local best = global best? → Greedy.
  6. Optimization with overlapping subproblems? → Dynamic programming.
  7. Searching for valid configurations? → Backtracking (add bounds → branch & bound for optimization).
  8. Exact answer too costly (NP-hard)? → Randomized / approximation / heuristics.
