§What is problem framing?

Problem framing is the process of analyzing a problem to isolate the individual elements that must be addressed, so you can decide whether machine learning is a viable, worthwhile approach — and if so, define precisely what the model should predict and how you'll know it worked. It happens before any data collection or model training.

A well-framed problem answers three questions:

  1. What is the problem, stated in non-ML terms?
  2. Is ML the best way to solve it?
  3. If yes, what exactly should the model predict, and how will we measure success?
Getting framing wrong is the most expensive mistake in an ML project: you can build a technically excellent model that solves the wrong problem, or that can never move the metric you actually care about.

1Understand the problem

State the ideal outcome — independent of the model

Describe what you want to happen for the user or business, not what the model does. The ideal outcome should still make sense to someone who has never heard of ML.

  • ✅ "Operators adjust the process before product quality drops."
  • ❌ "The model predicts a quality score." (that's a mechanism, not an outcome)

Find the existing (non-ML) solution

There is almost always a current approach — a heuristic, a rule, a human doing the task. Write it down. It becomes your baseline: it tells you how much value ML must add, and sometimes reveals that ML isn't needed at all.

Confirm you actually need a prediction

ML produces predictions. If your problem doesn't require predicting something uncertain, you probably don't need ML.

2Is ML the right approach?

ML is a strong fit when several of these hold:

Use ML when…Avoid ML when…
The patterns are complex and hard to express as explicit rules.A simple heuristic or rule already works well.
You have (or can obtain) many relevant labeled examples.You have little or no representative data.
The patterns change over time, so learning beats hand-coding.You need fully deterministic, 100% explainable output.
Occasional wrong predictions are tolerable.Any single error is unacceptable / safety-critical without guardrails.

Always build the dumb baseline first

Compare any ML idea against a trivial rule (e.g. "always predict the majority class", or a fixed threshold). If the baseline is good enough, ship it — and you've saved months.

Predictive vs. Generative ML

Predictive outputs a number or a class (price, defect / no-defect). Generative outputs content (a caption, a synthetic image, text). Knowing which you need shapes everything downstream.

3Frame the ML problem

Define the model's goal

Turn the ideal outcome into a single, measurable prediction the model makes. The model's goal is narrow and technical; it must clearly serve the ideal outcome.

Identify the output (the label) and its type

What does one prediction look like — a class? a number? a box? a mask? The answer determines the problem type and the data you need to label.

Choose a proxy label when needed

Often the ideal outcome can't be measured directly, so you predict a proxy that correlates with it.

Proxy labels are risky

Example: ideal = "useful video"; proxy = "watched > 50%". A clickbait video can satisfy the proxy while failing the ideal. Always ask: where does my proxy diverge from what I actually want?

Define success metrics — distinct from model metrics

Model metricsSuccess metrics
Measure the model: accuracy, precision, recall, AUC, mAP, MAE.Measure whether solving the problem helped: scrap rate, revenue, support tickets, time saved.
Computed on a test set.Computed in the real world / from business KPIs.

A model can score 0.99 accuracy and still fail every success metric. Decide your success metrics — and the threshold that counts as "worth shipping" — before training.

5Connection to Computer Vision

Computer vision is just ML where the input is an image (or video). The framing steps are identical — the only thing that changes is that the label is something visual. First, map the vision task to a core ML problem type:

CV taskUnderlying ML problemModel output
Image classification(multiclass) classificationone label per image

Semantic segmentationper-pixel classificationa class mask

Anomaly / defect detectionclassification (often one-class)normal / anomalous

Worked example: defect detection on a production line

Imagine a camera over a conveyor (or a froth-flotation cell, or a mineral-sorting feed). Let's frame it step by step.

  • Ideal outcome (non-ML): "Fewer defective units reach the customer" / "Operators react before product grade drops." Notice this never mentions a model.
  • Is ML right? Defects vary in shape, texture, and lighting — hard to capture with fixed rules; and you have a continuous stream of camera frames = data. ML fits. Baseline: a simple brightness/edge threshold or periodic manual inspection.
  • Model's goal: predict, per frame, whether a defect is present — and where, if you need to act on its location.
  • Output & type: binary classification (defect / ok) if "is it bad?" is enough; object detection (boxes) if you must localize; segmentation if you must measure defect area.
  • Proxy label: "defective" is defined by QA inspectors, so labels are subjective and expensive, and true defects are rare. That framing decision drives your whole data strategy.
  • Model metric vs success metric: model = recall / precision / mAP; success = "scrap rate reduced 15%", "fewer customer returns". Track both — they can disagree.

The accuracy trap in CV

If 99% of units are fine, a model that always says "ok" scores 99% accuracy and delivers zero value. With rare-defect problems, frame success around recall and precision (or PR-AUC), never raw accuracy.

6CV-specific framing pitfalls

  • Class imbalance: defects/events are rare → accuracy lies. Use recall, precision, PR-AUC, and decide which error (false alarm vs. miss) costs more.
  • Label quality & ambiguity: who defines the ground truth, and do two annotators agree? Fuzzy labels cap your ceiling.
  • Domain shift: a new camera, lighting change, or product variant silently breaks a model trained on old conditions — plan for monitoring and retraining.
  • Localization vs. classification: "is there a defect?" (cheap labels) is a very different problem from "where is it?" (expensive boxes/masks). Don't over-scope.
  • Annotation cost: bounding boxes and pixel masks are far more expensive to label than image-level tags — factor this into feasibility.

✓One-page framing checklist

  1. Stated the ideal outcome with no mention of a model?
  2. Identified the current non-ML baseline?
  3. Confirmed the problem needs a prediction, and that ML beats the baseline?
  4. Defined a single, measurable model goal tied to the outcome?
  5. Named the output / label and its problem type?
  6. If using a proxy label, written down where it can diverge?
  7. Chosen success metrics separate from model metrics, with a "ship it" threshold?
  8. (CV) Picked metrics that survive class imbalance?
